# TERRAIN-01C4 地下水・湿地水文 実装記録

- 更新日: 2026-10-22
- 対象PR: TERRAIN-01C4-A/B/C/D/E
- 状態: C4-AはPR #39のmerge commit `2abaa0c5`、C4-BはPR #40のmerge commit `98a67b64`で完了。C4-C「湖水収支・泉」は初回実装の人間確認とcommit許可、PR #41レビュー修正版のUnity回帰まで完了し、人間再確認待ち
- 作業ブランチ: `terrain-01c4c-lake-springs`

## 1. 目的と前提

TERRAIN-01C4は、TERRAIN-01C2の固定地質とTERRAIN-01C3の8×8水文セルを使い、タイル単位の固定表流水、地下水、自然土壌飽和、湖水収支、泉、自然冠水、広域湿原ゲートを生成する。

現在の降雨、河川水位、土壌水分、灌水、排水、耕作、人工水路、採掘穴、配置Blockは入力にしない。固定生成結果は現在水文の初期条件と長期傾向を表し、プレイヤー操作で直接書き換えない。

既存の旧7Biome用`GeneratedTile.WaterBodyType`はC6まで表示互換のため維持する。C4は新水文の表流水を専用Bufferへ出力し、旧River・Pondノイズから地下水、湖区分、湿原を逆算しない。

## 2. 変更単位

- C4-A1 河道中心線: 水文セルごとの安定Anchor、D8辺に対応する有限経路探索、負座標・チャンク境界・生成順不変を純粋計算とテストで確定する。
- C4-A2 湖面候補・ECS接続: C4-A1の中心線へ渓流・河川幅を適用し、閉鎖流域内の標高未満タイルを末端からFlood Fillして、河道と湖面候補を4096件の固定表流水Bufferへ格納する。Chunk生成Job、状態ハッシュ、性能比較を更新する。
- C4-B1 局所地質補正: 4用途の固定設定と専用Salt、連続ポテンシャル、地下水専用の透水性・保持力補正式を純粋計算として実装する。基礎地質Definition、既存Buffer、表示は変更しない。
- C4-B2 地下水・自然土壌飽和のECS接続: 固定9地点平均、表流水涵養、地下水接続境界、タイル別飽和度、状態ハッシュ、固定Tick一括公開を実装する。
- C4-C 湖水収支・泉: 湖候補を淡水・塩水・一時湖へ確定し、抑制済み泉源と固定淡水小川を追加する。
- C4-D 自然冠水・湿原規模: 半径32タイルの恒久淡水源探索と4水文セルの広域規模判定を実装する。
- C4-E 監査・診断表示: 複数Seed監査、Gameビュー、Map Viewer、凡例、中央タイル情報を接続する。

各項目は実装、初心者向け日本語コメント、関連EditMode／PlayModeテスト、文書更新、AI確認を同じ変更単位に含める。人間確認とcommit許可を受けるまでcommitせず、次項目へ自動着手しない。

## 3. C4-Aの固定データ境界

新しい固定表流水Bufferは1論理チャンク4096件を行優先で保持し、各要素へ少なくとも次を記録する。

- 表流水種別: なし、渓流、河川、湖面候補、後続の恒久淡水湖・恒久塩湖・泉流。
- 固定水面または河道の標高。
- 供給元の`RunoffEquivalentCells`または`LakeFillFraction`。
- 地下水涵養候補、確定自然水面、淡水接続を区別するフラグ。

河道は水文セルのD8辺をタイルへ描き下ろすだけで、流向や集水結果を再計算しない。湖面候補は最大4,096水文セル・262,144タイルの固定上限内で流域末端から連結したタイルだけを採用する。途中まで生成した結果は公開しない。

### 3.1 C4-A2の実装結果

`GeneratedSurfaceWaterTile`は1タイル16 bytesで、次の値を保持する。

- `Type`: `None`、`Stream`、`River`、`LakeCandidate`。C4-A2で予約した恒久淡水湖、恒久塩湖、泉流をC4-Cで使用する。
- `Flags`: 地下水涵養候補、確定自然表流水、淡水接続、河道中心線を独立したbitで保持する。C4-A2の渓流・河川は涵養候補・確定自然表流水・淡水接続を設定する。湖面候補は涵養候補だけを設定し、後続区分前に恒久水面や淡水と断定しない。
- `SurfaceHeight`: 河道は対象タイルの連続標高、湖面候補は固定湖面標高を保持する。
- `SourceAmount`: 河道は`RunoffEquivalentCells`、湖面候補は`LakeFillFraction`を保持する。
- `SourceCellX`、`SourceCellY`: 重なり解決と監査に使う供給元水文セルの絶対座標を保持する。

河道はタイルから逆算した実際の担当水文セル9×9へ1セルのHaloを加えた11×11を供給元として走査し、境界外から流入する中心線と河川幅も同じ絶対座標規則で生成する。64×64タイルでは中心`-4〜+3`の担当規則により、正側末尾4タイルを9個目の水文セルが担当するため、64件のローカル水文Bufferだけをチャンク交差範囲とみなさない。渓流は中心線だけ、河川は中心線と上下左右1タイルを候補にし、斜め角を埋めない。重なりは河川、流出寄与の大きい供給元、水文セルY、Xの昇順で代表値を一意に決める。`ChannelCenterLine`はその代表選択と独立し、別河道の幅と中心線が交差する場合も候補間の論理和として保持する。元の連続標高が海面未満のタイルは淡水候補へしない。

地下水涵養用の9×9中間値も生成する場合は、河道供給元をさらに1セル広い2セルHaloの13×13まで走査する。隣接セルの外端にある中心線から広げた河川幅1タイルは供給元から2セル先の担当範囲へ入れるため、この追加Haloがないと共有境界セルの涵養有無が生成元チャンクによって変わる。追加走査は地下水入力を要求する経路だけに限定し、表流水だけの11×11走査と4096件の表流水結果は変更しない。

湖面候補はC3-D1と同じ流域集合と固定湖結果を再構築し、末端Anchorから8近傍Flood Fillする。湖の代表セルも実際にチャンクと交差する9×9を調べ、ローカルBuffer外の正側17セルは河道走査で生成した基礎水文を固定長キャッシュから再利用して湖状態だけを追加する。同じ閉鎖末端は64bit座標Keyで一度だけ処理する。流域外、湖面標高以上、海面未満へは進まず、同標高の飛び地を採用しない。水文セルの9地点平均では陸上でも、末端セル内の最低Anchorだけが海面未満の場合は、海水で分断された別タイルへ開始点を移さず、その流域を淡水湖候補なしとして正常終了する。対象チャンク内の候補数を先に数え、候補がない場合は全流域Flood Fillを省略する。訪問配列は条件外と到達済みを区別して連続標高の再計算を防ぎ、対象チャンク内の全候補へ到達した時点で終了する。固定上限、座標検証、元地形生成、流域所属の不整合に失敗した場合は、途中結果をECSへ公開しない。

`ChunkGenerationSystem`は基礎水文8行、閉鎖流域の準備、最大8担当の湖解決、タイル表流水の順に依存させ、地形・資源系列とは並列にする。既定2枠のPersistent作業配列へ、4096件の表流水結果、256件の経路ノードと経路、262,144件のFlood Fill状態とQueueを追加した。完了後は地形4096件、資源4096件、水文64件、表流水4096件の4 Bufferを同じ固定Tick公開境界で検証・コピーする。表流水生成の失敗を含む場合は4 Bufferのどれも公開しない。

状態ハッシュは水文結果に続けて4096件の表流水結果を行優先で含める。単一チャンクAPIも製品Jobと同じ表流水生成器を使うため、生成順やロード状態に依存しない。

## 4. 局所地質補正

亀裂、風化帯、粘土層、帯水層は別Saltの連続ポテンシャルとして生成する。補正値は地下水と自然土壌飽和だけが参照し、`GeneratedTile`の基礎透水性・地下水保持力、地質Definition、資源、Biomeへ書き戻さない。

水文セルの地下水には固定9地点の補正後平均、タイルの土壌飽和には対象タイルの補正後値を使う。これにより広域地質と局所変化を両立しつつ、水文セル境界だけで飽和域が四角くなることを防ぐ。

### 4.1 C4-B1の実装境界

`GroundwaterGenerationSettings`は、亀裂128タイル、風化帯96タイル、粘土層192タイル、帯水層256タイル、各3オクターブ、Support中央値32,768、仕様で確定した8個の除数を保持する。`WorldGenerationSettings`とAuthoring Snapshotは共有既定値を値コピーし、Inspectorへ同じ設定を重複保持しない。

`DeterministicGroundwaterGenerator`は、絶対タイル座標から4用途別Saltの連続ポテンシャルを生成し、基礎透水性・地下水保持力へ符号付き64bitで全項を合成してから0〜65,535へ一度だけ飽和する。補正後値は戻り値にだけ保持し、`GeologyDefinition`、`GeneratedTile`、資源適性、Biome、既存地質の状態ハッシュを変更しない。C4-B1では純粋計算までを完了条件とし、固定9地点平均、地下水ポテンシャル、自然土壌飽和、ECS公開、性能・メモリ増分はC4-B2へ残す。

### 4.2 C4-B2のECS接続

`DeterministicSurfaceWaterGenerator`は、表流水4096件と同じ有限走査から、チャンクと交差する完成水文9×9件と、各セル内に自然河川・渓流・湖面候補が存在するかを示す81件の涵養フラグを出力する。正側末尾4タイルを担当する9個目の水文セルと、負側へ張り出す担当範囲も絶対タイル座標から判定し、ロード済みチャンク範囲へ依存しない。

`DeterministicGroundwaterHydrologyGenerator`は、各水文セル中心の`-3／0／+3`固定9地点で補正後透水性・地下水保持力を整数平均する。基礎湿度、`RunoffEquivalentCells×2,048`を65,535へ飽和した値、自然表流水候補の65,535の最大を涵養値とし、補正後透水性・保持力の小さい方との64bit積を65,535で整数除算して`GroundwaterPotential`を得る。32,768以上では既存の接続bitを保ったまま`Groundwater`を追加するが、自然表流水や現在水文は変更しない。

自然土壌飽和は4096タイルそれぞれについて、担当水文セルの基礎湿度と地下水を各2、対象タイルの排水しにくさと平坦さを各1として64bit合成し、合計6で整数除算する。結果は2 bytesの`GeneratedHydrologyTile.NaturalSoilSaturationPotential`として1チャンク4096件の専用Bufferへ保持する。39,321の飽和境界は設定へ固定するが、湿原Biomeへの昇格は後続C4-Dの低地・淡水接続・自然冠水条件と合わせて行う。

`ChunkGenerationSystem`は、表流水Jobと地形・資源Jobの完成Handleを結合した後に地下水Jobを実行する。生成枠では9×9完成水文、81涵養フラグ、4096自然水文を所有し、地形、資源、地下水反映済み水文、表流水、自然水文の5 Bufferを同じ固定Tick境界で公開する。先行段階または地下水段階が失敗した場合は5 Bufferのどれも公開しない。状態ハッシュも地下水反映済み64水文セル、4096表流水、4096自然水文を固定順で含む。

## 5. C4-Cの湖水収支・泉

`LakeSpringGenerationSettings`は、湖水収支の比重2：1：1と合計4、一時湖／塩湖境界26,214、塩湖／淡水湖境界52,428、泉の地下水／落差比重2：1と合計3、落差倍率16、放出境界39,321、抑制半径4水文セルを保持する。`DeterministicLakeSpringGenerator`は湖末端の充填率、地下水、地形気温、基礎湿度から64bit整数で水収支を求め、越流淡水湖、一時湖、恒久塩湖、閉鎖淡水湖へ分類する。一時湖は`LakeCandidate`の涵養履歴だけを残して固定自然水面を外し、塩湖は固定自然水面を維持して淡水接続を外す。

泉は対象チャンクへ入り得る11×11泉源と、その周囲4セルの抑制比較に必要な19×19候補、候補の8近傍に必要な21×21完成水文から決める。地下水接続があり、恒久自然水面がなく、地下水のない低い隣接セルを持ち、放出度39,321以上となるセルだけを候補にする。半径4セル内では放出度最大、同値時は水文セルX・Y昇順の一つだけを残す。泉源から最低適格隣接セルへの合成辺は経路細分化の作業値にだけ設定し、公開する基礎D8、`CatchmentAreaCells`、`RunoffEquivalentCells`を変更しない。

PR #41レビュー後は、通常表流水Jobが生成済みの河道中心線と上下左右1タイルの河川幅を、同じ海面判定のまま泉用21×21涵養キャッシュへ同時記録する。Haloセル自身の`ConnectionFlags`だけから涵養を近似せず、隣接河川幅だけがセルへ入る場合も所有チャンクと同じ地下水接続へ更新する。泉流の細分化経路も通常河道と同じく連続標高が海面未満のタイルを維持し、`SpringStream`または淡水接続で海水域を上書きしない。

湖水収支の最終区分後は、交差9×9で確定した`Lake`接続だけを対応する泉用21×21キャッシュへ同期する。一時湖が正側境界の9個目セルにある場合も隣接チャンクと同じ泉候補判定にし、通常河道の涵養再構築で先に更新した地下水値と`Groundwater`接続は上書きしない。

製品`ChunkGenerationSystem`は地下水Job後に、21行を既存8組の集水Heap・閉鎖流域配列・Hash領域へ剰余分割して周辺水文を並列生成し、最終Jobで湖区分と泉流を適用する。帯水係数は地下水ポテンシャルの上限でもあるため、外周セルの固定9地点補正後透水性・保持力の小さい方が32,768未満なら、最大涵養でも泉源にならないことを証明して代表標高だけを生成し、最大4,096セルの集水探索を省略する。最終Handle、`ChunkGenerationLakeSpringWait`、状態ハッシュ、失敗通知を既存5 Bufferの一括公開境界へ接続し、途中失敗時はどのBufferも公開しない。

C4-Cは既存ECS Buffer要素を拡張せず、Persistent生成枠へ21×21の`GeneratedHydrologyCell` 42,336 bytes、19×19の`SpringCandidate` 8,664 bytes、8担当の失敗通知8 bytesを追加する。PR #41レビュー修正では、通常河道から泉Haloへ渡す1 byte×441件の涵養キャッシュを追加し、合計51,449 bytesとする。1枠は9,747,385 bytes、既定2枠は19,494,770 bytes（約18.59MiB）となる。`SpringCandidate`は24 bytesである。コンテナ管理領域、Allocator余白、安全性情報は含めない。
